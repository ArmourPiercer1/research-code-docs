## P1 — Orchestrated eval runaway: 63M tokens / 11 h for zero data (2026-08-04)

- **What happened.** The Phase D.3 re-run was launched as a background Workflow whose `args` (intended as an array of cases) arrived as a JSON **string**; the script iterated it character-by-character and spawned one agent per character, "hit[ting] the 1000-agent cap after ~63M tokens / ~11h before failing (`WorkflowAgentCapError`)". No corpus/skill/result file was written (`dqe-v0.4.1-diagnostic-close.md:41-44,46-48`; `benchmark-changelog.md:95-98`).
- **When.** 2026-08-04 (between commits `14959a8` and `0585574`). Same bug class had already killed the first 26-run matrix launch at 0 agents / 0 tokens on 2026-07-31 (`dqe-blind-matrix-investigation-2026-07-31.md:99` "首次因 `args` 被序列化成字符串失败于 0 子代理、0 token，已修").
- **Cost.** ~63M tokens + ~11 h, zero data, zero metric value; then the D.3 re-runs had to be "redone as 7 controlled direct Agent calls" (`benchmark-changelog.md:98-99`), including BP-006-audit ×3 (which itself first came back 3-way unstable — see P4); and an entire pre-flight validator regime had to be built before any further launch: `make_phase_e_plan.py` → `validate_eval_plan.py` ("aborts before the first agent on string-`runs`, dup run_key, >`MAX_EVAL_RUNS=64`…", `benchmark-changelog.md:132-134`).
- **Addressed by.** Static, pre-counted, hash-verified eval plans; hard caps (MAX_EVAL_RUNS=64, MAX_BATCH_SIZE=4, MAX_RETRIES_PER_SLOT=1, `dqe-v0.4.1-diagnostic-close.md:54-59`); `BACKGROUND_WORKFLOW_FOR_ADMISSION=FORBIDDEN` (`benchmark-changelog.md:116,129-131`).
- **Unresolved.** The failure class recurred because the first occurrence (2026-07-31, 0-cost) was fixed ad hoc ("已修") instead of being promoted to a mechanical pre-launch check; the root fix lives in a validator script, not in the harness API that serializes `args`; non-admission runs may still use background workflows with the same hazard.
